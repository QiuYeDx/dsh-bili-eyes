# 门卫协议 v1

dsh-bili-eyes 的写操作（点赞、评论、私信、动态、关注）要回答两个问题：

- **这个会话是不是主人本人**：可信会话里「直接发」才真的直接发，「先问主人」才能当场问。
- **主人有没有同意**：草稿发出前，要确认主人在草稿之后说过同意的话（「可以」「嗯」「关注吧」都行，插件自己判断）。

收件箱有新消息时，还要有人把它转达给主人。

插件自己不知道消息是从 QQ 群、私聊还是本机窗口来的，这些交给「门卫」回答。门卫有三种，插件按顺序用第一个可用的：

| 顺序 | 门卫 | 适合谁 |
| --- | --- | --- |
| 1 | **进程内服务**：跑在 DSH 里的桥接插件提供 `biliEyesGate` 服务 | 官方 qqbot、微信插件这类在 DSH 进程里的桥接 |
| 2 | **HTTP 门卫**：设置页填的「门卫地址」（只能是本机地址） | 独立进程的桥接，比如 NapCat + 看门狗 |
| 3 | **内置门卫**：按会话的 `agentPreset`、工作目录推断 | 没有桥接、只在 DSH 桌面版里用 |

门卫没响应、返回格式不对时，一律按「不可信 / 没同意 / 没转达」处理。

## 动作

每个请求都是一个 JSON 对象，`action` 决定做什么。HTTP 门卫用 `POST`，返回 JSON。进程内服务就是同名的异步方法，参数是同一个对象。

### `hello`：握手（v1 新增，可选）

```json
{ "action": "hello", "protocol": 1 }
```

返回：

```json
{ "protocol": 1, "actions": ["hello", "context", "ownerMessages", "notify"], "name": "大肥鱼看门狗" }
```

不支持 `hello` 的门卫当成 v0。v0 和 v1 的其他动作完全一样，v1 只是在请求里多带一个 `session`。设置页「测试门卫」会显示协议版本。

### `context`：这个会话可信吗

```json
{
  "action": "context",
  "sessionId": "DSH 会话 id",
  "session": { "agentPreset": "qq-chat", "cwd": "E:\\fish\\qq", "parentSession": "", "rootSession": "根会话 id" }
}
```

返回 `{ "trusted": true, "label": "主人私聊" }`。`label` 会显示在草稿和设置页上，写给人看。

- `session` 是 v1 新增的，取自 DSH 会话头。子代理会话会沿 `parentSession` 一路找到根会话，`rootSession` 就是根会话的 id。旧门卫忽略它也没关系。
- 设置页「测试门卫」会发 `sessionId: "gate-test"`，门卫返回什么 `label` 都行，只要能响应。
- 只有确定是主人本人时才返回 `trusted: true`。群聊、别人的私聊、拿不准的，一律 `false`。

### `ownerMessages`：主人在某个时间之后说过什么

```json
{ "action": "ownerMessages", "sessionId": "…", "since": 1793300000000, "session": { "…": "同上" } }
```

返回 `{ "messages": [{ "at": 1793300012000, "text": "发 #3" }] }`。`at` 是毫秒时间戳。

- 只返回**主人本人**发的消息，别人说的不能放进来。
- 范围：至少要有主人和她的私聊。草稿是在群里起的，也要加上那个群里主人说的话。
- 插件自己判断哪句算同意：短句、新的优先，带编号的只对那条草稿有效。门卫不用理解内容。

### `notify`：转达给主人

```json
{ "action": "notify", "kind": "inbox", "text": "【B站收件箱】…（给模型看的一段文字）", "items": [{ "id": "r12", "kind": "reply", "user": { "name": "…" } }] }
```

返回 `{ "ok": true }`。转达失败就返回 `false`。`kind`（v1 新增，没有就当 `inbox`）：

| kind | 什么时候 | items |
| --- | --- | --- |
| `inbox` | 收件箱有新消息（回复、@、主人的私信） | 收件箱条目；`ok: true` 的会被标记成「已转达」，不再重复转达，失败下次再试 |
| `recommend` | 插件「自己逛」逛到想推荐给主人的视频，主人选了「门卫转达」 | `[{ bvid, title, why, url }]`；失败不重试 |

怎么转达由门卫决定，最好让她用自己的口吻说。看门狗的做法：

- **inbox**：改写桥接里一个停用的定时任务「B站收件箱」，把新消息附在指令后面，再立刻运行它，让她在主人私聊里醒来处理。
- **recommend**：用另一个停用任务「B站推荐」，没有就自动建一个。
- 桥接不可用时：直接用 QQ 私聊主人一句。

## 进程内服务

桥接插件在自己的 `apply` 里注册服务：

```js
export function apply(ctx) {
  ctx.set('biliEyesGate', {
    async hello() { return { protocol: 1, actions: ['hello', 'context', 'ownerMessages', 'notify'], name: 'my-bridge' }; },
    async context({ sessionId, session }) { /* 查自己的会话表 */ return { trusted: false, label: 'QQ 群' }; },
    async ownerMessages({ sessionId, since }) { return { messages: [] }; },
    async notify({ text, items }) { return { ok: true }; },
  });
}
```

插件每次调用时用 `ctx.get('biliEyesGate')` 去取，桥接晚加载、重载都没关系。每个方法 3 秒内要返回，超时按失败算。

有了这个服务，插件就不再用 HTTP 门卫和内置门卫。

## 内置门卫

没填门卫地址、也没有桥接提供服务时使用。

**判定**：从调用工具的会话出发，沿 `parentSession` 找到根会话。链上任何一层的 `agentPreset` 符合下面的正则，或者工作目录在「不可信目录」下，就当成桥接会话（不可信）。

- 正则默认是 `qq|wechat|weixin|wx|onebot|napcat|bot|group`，不分大小写。
- 两项都能在设置页「收件箱 → 门卫」里改。
- 设置页「概览 → 安装检查」列出最近的会话和判定理由。

**这是推断，不是认证。** 它能挡住常见的桥接（比如 qq-bridge-enhanced 的 `qq-chat*` 会话），挡不住刻意伪装的。要严格区分主人和群友，请用桥接提供的门卫。

**可信会话**：

- 「直接发」照常直接发。
- 「先问主人」会弹 DSH 原生审批卡片，主人在同一轮里点「允许」就发，点「拒绝」就不发。
- 没有窗口能弹卡片时，照常起草，等主人在设置页同意。

**桥接会话**：不管档位，一律只起草，只能在设置页同意。

不在桥接会话里弹卡片的原因：桥接可能把审批转发到群里，群里谁都能点「允许」。

**收件箱**：内置门卫没处转达。新消息留在收件箱里，她下次用任何 B站工具时，结果末尾会提一句「收件箱有 N 条新消息」。设置页「收件箱」也能看。

## 工具清单

桥接给工具做白名单时，直接用插件导出的清单，不用按名字一个个写：

```js
import { READ_TOOLS, WRITE_TOOLS } from 'dsh-bili-eyes/tool-list';
```

- 只读工具返回的都是公开内容，群聊里放开也安全。
- 写工具受插件自己的档位、额度和门卫约束，要不要在群聊里放开由桥接决定。

## 参考实现

作者自用的看门狗（`fish-watchdog/watchdog.mjs`，没有公开）里的 `gate()`，思路可以照搬：

- `context`：用桥接的会话表 `state/sessions.json`，把 DSH 会话 id 反查成 `private:<QQ>` / `group:<群号>`。
- `ownerMessages`：用 OneBot 的 `get_friend_msg_history` / `get_group_msg_history` 取主人的原话。
- `notify`：用桥接的定时任务叫醒她。
