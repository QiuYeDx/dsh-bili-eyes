# 冲浪与互动：设计（0.5.0）

让 AI 用一个 B站账号（建议是专门的小号）**自己逛 B站、看收件箱、点赞收藏、评论和回复、私信主人、发动态**。
0.4.0 之前插件只会「看一个视频」和「搜视频」。这一版加的东西分四层，由低风险到高风险：

| 层 | 能力 | 工具 |
|---|---|---|
| 读 | 首页推荐、热门、排行、关注动态、UP 主投稿；评论区和楼中楼 | `bili_feed`、`bili_comments` |
| 冲浪 | 在插件内部逛一圈：挑候选 → 快速看几条 → 交一份摘要 | `bili_surf` |
| 收件箱 | 回复我的、@ 我的、私信，记账并转达 | `bili_inbox`（另有后台轮询） |
| 写 | 点赞/收藏、评论/回复、私信（只发主人）、动态 | `bili_like`、`bili_comment`、`bili_dm`、`bili_post`、`bili_confirm` |

参考了 [c1overzz/dsh-bili-scroll](https://github.com/c1overzz/dsh-bili-scroll) 和它的分支
[Yuuyuko-uu/dsh-bili-subagent](https://github.com/Yuuyuko-uu/dsh-bili-subagent)（都是 MIT），主要参考两点：一是接口用法，以它们内置的 bilibili-mcp 为准；二是收件箱的记账方式。
代码全部用 JS 重写，不引入 Python。没有沿用的部分是「派 DSH 子代理」和「往会话里塞消息」，原因见第 3 节。

## 1. 原则

1. **写操作默认全关。** 每类写操作有三档：`off` 关、`approve` 先起草等主人同意、`auto` 在额度内直接发。设置页里逐项打开。
2. **只有主人能让它动手。**
   - 群聊里谁都能跟 AI 说话，所以「发出去」这一步必须核实是主人的意思。
   - 核实交给可选的「门卫」接口（第 6 节）。
   - 没配门卫时，只能在设置页点「同意」。
3. **硬上限写在代码里，模型改不了。**
   - 每天的条数、两次写之间的间隔、同一视频只评论一次。
   - @ 只能 @ 主人，私信只能发给主人。
   - 正文不许带链接或长串数字。
4. **看得见、撤得回。**
   - 所有写操作进审计日志。
   - 发出的评论可以在设置页删掉。
   - 设置页有一个「全部停下」开关。
5. **素材不是指令。** 标题、简介、字幕、评论、私信里的文字一律当素材，返回给模型时加上提示（沿用 `MATERIAL_NOTE` 的做法）。
6. **逛的过程不进主会话。** 会话上下文很贵，`bili_surf` 在插件里用一个便宜的模型挑选、总结，只把摘要交回去。

## 2. 读：`bili_feed`、`bili_comments`

**`bili_feed({ source, up, limit })`**

| source | 接口 | 要登录 |
|---|---|---|
| `recommend` 首页推荐 | `x/web-interface/wbi/index/top/feed/rcmd`（WBI） | 登录后按账号口味推荐 |
| `hot` 热门 | `x/web-interface/popular` | 否 |
| `rank` 排行 | `x/web-interface/ranking/v2` | 否 |
| `following` 关注动态里的视频 | `x/polymer/web-dynamic/v1/feed/all?type=video` | 是 |
| `up` 某个 UP 主的投稿 | `x/polymer/web-dynamic/v1/feed/space?host_mid=`（空间投稿接口风控重，用动态接口代替） | 否 |

返回格式和 `bili_find` 一样：标题、UP、时长、播放、日期、链接、一句简介。

**`bili_comments({ url, rpid, sort, limit })`**

- 不给 `rpid` 时看评论区（`x/v2/reply/wbi/main`，按热度或时间排）。给了 `rpid` 时看这一条下面的楼中楼（`x/v2/reply/reply`）。
- 每条评论带上 `#rpid`，回复时要用。

## 3. 冲浪：`bili_surf({ direction, picks })`

**为什么不用 DSH 子代理。** 子代理是一个完整的 agent，它能用哪些工具取决于宿主的 preset。从受限会话（比如 QQ 群）派出去时，工具范围不一定可控，而它要读的又全是 B站上谁都能写的文本。所以这里在插件内部跑一个**固定流程**：

1. **找候选**：
   - 给了 `direction` 时，按关键词搜（综合 + 最新）。
   - 没给时，用首页推荐 + 热门。
   - 然后去掉最近 7 天逛过的、超过 `surfMaxSeconds` 的，共 `surfCandidates` 条（默认 24）。
2. **挑**：一次模型调用。把候选清单和「口味」（设置里的 `surfTaste`）交给模型，让它挑出最多 `surfPicks` 条（默认 3），每条附一句理由。
3. **快速看**：不做分镜，只取文字材料。包括信息、标签、官方 AI 总结、字幕前一段、热评前几条。
4. **总结**：一次模型调用。每条写「讲了什么 / 亮点 / 评论区在聊什么」，不超过 100 字。
5. **交回**：返回摘要和链接，并提示「想细看就用 `bili_look`」。

补充说明：
- 一共两次模型调用。模型用设置里的 `surfModel`（`provider/model`）；留空时用调用它的会话所用的模型，再不行用宿主默认。
- 宿主没有 `llm` 服务时，按播放量和新旧挑选，直接返回材料。
- 节流：每小时最多 `surfPerHour` 次。

## 4. 收件箱：后台轮询 + `bili_inbox`

- **轮询**：`inboxOn` 打开后，每 `inboxIntervalSeconds` 秒（默认 180）查一次，`inboxQuiet` 时段（默认 `00:30-07:30`）不查。
  - 回复我的：`x/msgfeed/reply`
  - @ 我的：`x/msgfeed/at`
  - 私信：`session_svr/v1/session_svr/get_sessions` + `svr_sync/v1/svr_sync/fetch_session_msgs`
- **记账**：存在 `$DSH_HOME/bili-eyes/inbox.json`。
  - 每条记录包含：`id`、类型、时间、对方、原文、视频、回复所需的 `oid/type/root/parent`、我当时那条评论的原文。
  - 状态四种：`new` 新的、`notified` 已转达、`done` 处理完、`ignored` 忽略。
  - 第一次运行只记基线，不把历史消息当新消息。
- **转达**：有新的就调门卫的 `notify`，同一条只转达一次，每小时最多 `inboxNotifyPerHour` 次。没配门卫时只在设置页显示。
- **`bili_inbox({ action: 'list' | 'done' | 'ignore', ids })`**：模型用它看待处理的消息、标记已处理。要回复就用 `bili_comment` 并带上 `inbox` 编号。

## 5. 写

| 工具 | 做什么 | 接口 | 档位键 | 每日上限键 |
|---|---|---|---|---|
| `bili_like({ url, fav })` | 点赞；`fav: true` 时同时收进默认收藏夹 | `x/web-interface/archive/like`、`x/v3/fav/resource/deal` | `likeMode` | `likePerDay` |
| `bili_comment({ url, text, rpid, inbox, mention })` | 评论；给 `rpid` 或 `inbox` 时是回复（楼中楼）；`mention: true` 时 @ 主人 | `x/v2/reply/add`（@ 用 `at_name_to_mid`） | `commentMode` | `commentPerDay`、`replyPerDay` |
| `bili_dm({ text })` | 私信主人（`ownerMid`），不能发给别人 | `api.vc.bilibili.com/web_im/v1/web_im/send_msg` | `dmMode` | `dmPerDay` |
| `bili_post({ text })` | 发一条纯文字动态 | `x/dynamic/feed/create/dyn` | `postMode` | `postPerDay` |
| `bili_confirm({ draft, decision })` | 按主人的意思发出或丢掉草稿 | — | — | — |

**一次写操作的流程：**
1. **找到档位**：档位是 `off` 时直接拒绝。
2. **内容检查**：
   - 长度：评论 ≤ 300 字，私信 ≤ 500 字，动态 ≤ 500 字。
   - 不许出现链接，不许出现 5 位以上的连续数字。
   - `@某人` 只允许 @ 主人；楼中楼里不手打 @，B站会自己加。
   - 同一视频的顶层评论只发一次，同一条楼中楼最多回 2 次。
3. **额度检查**：看当日条数和 `writeGapSeconds` 间隔。
4. **决定直接发还是先起草**：
   - 档位是 `auto`，并且调用它的会话可信（门卫的 `context` 返回 `trusted`；没配门卫时视为可信）→ 直接发。
   - 否则起草：存进 `drafts`，编号 `#n`，返回「已起草 #n，还没发。问主人要不要发；主人同意后调用 `bili_confirm`」。
5. **`bili_confirm` 怎么判定**：
   - 向门卫要「草稿之后主人说过的话」（`ownerMessages`）。
   - 找到「发 / 可以 / 行 / 好 / ok / 发吧 / 同意」（可带编号）就发；找到「不发 / 别发 / 算了 / 不要」就丢掉。
   - 都没有就回「主人还没同意」。
   - 没配门卫时，只能在设置页「互动 → 待同意」里点。
   - 草稿 `draftMinutes`（默认 60）分钟后过期。
6. **发出后**：记审计（时间、类型、正文、目标、结果、`rpid`），失败不扣额度。
   - B站返回的错误照原样给模型。常见的有：未转正不能评论、`-352` 风控、`12015` 要验证码、`-111` csrf 失效。
   - 碰到风控类错误自动暂停写操作 30 分钟。

**不做的事**：投币（会花硬币）、关注和拉黑、改资料、上传视频、批量操作。

## 6. 门卫接口（可选）

插件本身不知道「主人是谁、这条消息是从哪个聊天来的」。这些交给一个本机 HTTP 接口回答。
设置项是 `gateUrl`（例如 `http://127.0.0.1:3398/gate`），可以再加一个请求头 `gateHeader`（例如 `x-fish: 1`）。
所有请求都是 `POST` JSON，3 秒超时。**门卫没响应时一律按「不可信 / 没同意」处理。**

| action | 请求 | 返回 |
|---|---|---|
| `context` | `{ action, sessionId }` | `{ trusted: boolean, label: string }`。`trusted` = 这个会话就是主人本人，比如主人私聊 |
| `ownerMessages` | `{ action, sessionId, since }`（毫秒） | `{ messages: [{ at, text }] }`：`since` 之后主人在私聊里，以及在这个会话所在的群里说过的话 |
| `notify` | `{ action, text, items }` | `{ ok: boolean }`：把收件箱的新消息转告给 AI 或主人 |

## 7. 设置页

页签：概览 / 试看 / **冲浪** / **收件箱** / **互动** / 设置。

- **冲浪**：
  - 预览五种 feed（卡片）。
  - 「逛一圈」试跑 `bili_surf`。
  - 设置口味、模型、条数。
- **收件箱**：
  - 消息列表（按状态筛选，可标处理完或忽略）。
  - 「现在查一次」。
  - 设置轮询开关、间隔、安静时段、门卫地址，门卫有「测试」按钮。
- **互动**：
  - 主人 UID（填后显示昵称核对）。
  - 四类档位和各项上限。
  - 待同意的草稿：同意或丢掉。
  - 已发记录：可删除评论。
  - 「全部停下」开关。
- 新增的设置项继续由 `config.js` 的 `FIELDS` 生成。新增两种字段类型：`enum`（下拉）和 `text`（单行或多行）。

## 9. 数据文件（都在 `$DSH_HOME/bili-eyes/`）

| 文件 | 内容 |
|---|---|
| `inbox.json` | 收件箱账本：基线游标 + 每条的状态 |
| `drafts.json` | 草稿 |
| `actions.jsonl` | 写操作审计，只追加，超过 2000 行时截成最近 1500 行 |
| `surf-seen.json` | 逛过的 BV 号和时间，保留 7 天 |
| `history.jsonl` | 和以前一样，新增 `kind`：`feed`、`surf`、`comments` |

## 10. 测试

- **单元测试**用假的 `fetch`：
  - 核对每个写接口的地址、表单字段、csrf。
  - 核对内容检查、额度、档位与可信判断、草稿同意词的解析、收件箱的基线和去重、门卫超时按不可信处理。
- **读接口**用真实账号跑一遍（只读）。
- **写接口**只做假 `fetch` 测试。真实发送要等账号转正，并且只在主人明确同意后，在设置页手动试一条。
